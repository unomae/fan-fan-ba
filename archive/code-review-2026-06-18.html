一句話結論

翻翻吧已經有清楚差異化：即選即用、AI 解釋 / 優化、Obsidian 留存、Google Drive 設定同步。下一階段最值得先做的不是堆更多功能，而是把「安全、可維護、上架審核可信度、日常閱讀不打擾」補強；這些會直接影響 Chrome Web Store 審核、使用者信任，以及後續功能速度。

Findings

P0

密碼欄位目前被視為可翻譯文字來源

isTextSelectionControl 把 password 放進允許清單。若使用者在密碼欄或敏感輸入欄選到文字，content script 可能讀取後送進 AI provider。這是隱私與上架審核風險。

建議：立即排除 input[type=password]，並評估預設排除信用卡、OTP、email、tel 等敏感欄位；必要時只允許使用者按快捷鍵明確觸發。

證據：content/main.js:167-171；Chrome 文件也提醒不要把敏感資料傳給 content script，且 content script 互動要謹慎。

✅ 已完成：改由 content/selection-controls.js 統一判斷可選取輸入欄，排除 password / email / tel / number 與 OTP / 信用卡 / CVV / billing / phone 等敏感欄位（含 autocomplete token 與 placeholder 比對），並補上 sensitive input regression tests。

P0

npm test 預設失敗，CI 入口不可信

目前同時存在 jest.config.js 與 package.json 的 jest key，Jest 無法隱式選擇設定檔，導致 npm test 直接失敗。

建議：保留單一 Jest 設定來源，或把 script 改成 jest --config jest.config.js；再補 GitHub Actions / PR check。

驗證：npm.cmd test -- --runInBand 失敗；npm.cmd test -- --runInBand --config jest.config.js 則 14 suites / 114 tests passed。

✅ 已完成：移除 package.json 內重複 Jest 設定，改以 jest.config.js 為單一設定來源。目前 npm test 一條指令即通過：15 suites / 123 tests passed。

P1

<all_urls> + all_frames: true 的常駐注入面積偏大

所有頁面、所有 frame 都載入 10 個 content scripts 與大型 CSS。以使用者體感來看，這容易在 Google Docs、Notion、內嵌 iframe、企業內部系統或高 DOM 頁面造成干擾；以安全角度看，也會放大攻擊面。

建議：短期加入敏感網域 / iframe denylist 與效能 guard；中期改成可選站點啟用、activeTab 或 programmatic injection；至少把 page translation 這種重功能改成按需載入。

證據：manifest.json 的 content_scripts.matches=["<all_urls>"]、all_frames=true。Chrome 文件建議權限最小化、必要時使用 optional permissions。

P1

LLM / 使用者資料透過 innerHTML 渲染的面積太大

專案已有 escapeHtml 與結構化渲染，這是好事；但結果卡、floating ball、page translator 仍大量使用 innerHTML。AI 回傳內容、單字本、歷史紀錄、網頁文字都屬於不完全可信輸入，長期應降低 HTML 拼接依賴。

建議：建立 dom() / text() / safeHtml() 小型 render helper；AI markdown 渲染集中在一個白名單管線；新增 XSS payload 測試。

證據：content/result-card.js:446,459,474,481,706,715、content/page-translator.js:666,774,834,855、content/floating-ball.js:405,431。Chrome 安全文件明確建議避免 innerHTML。

P1

整頁翻譯模組過大，後續功能速度會被拖慢

page-translator.js 同時處理收集 DOM、狀態機、串流請求、清理結果、面板 UI、導航偵測、滑鼠互動與錯誤狀態。這種單檔會讓 bug 修復與 UX 實驗成本越來越高。

建議拆成 collector、translation-client、renderer、panel、state，先不改行為，只做可測試的機械拆分。

證據：content/page-translator.js 約 1,367+ 行；coverage 約 39.2% lines，未覆蓋集中在啟動流程、請求、渲染與 watcher。

P2

web_accessible_resources 對所有網站開放，可再收斂

目前字型與 icon 對 <all_urls> 可見。這不是立即漏洞，但 Chrome 文件指出 web-accessible resources 會讓 extension 更容易被網站偵測，也增加可利用面。

建議：確認 content script 是否真的需要公開字型；若只 extension pages 用，移出 web accessible；若 content UI 需要，縮到必要資源與更小 matches。

證據：manifest.json 的 web_accessible_resources。

軟體工程師視角

做得好的地方

  • Manifest V3 service worker 架構已到位，API Key 主要留在 background / storage 層。
  • 有 Secret migration，把 API Key 從 sync 移到 local，方向正確。
  • 有 retry / timeout / AbortController，對 AI provider 不穩定有基本韌性。
  • 測試數量不算少，核心 content 元件、options、cloud sync、storage 都已有 coverage。

優先改善

  • 先修 npm test 入口，讓所有人一條指令知道專案是否健康。
  • 把敏感輸入欄排除，尤其 password。
  • 為 background message handler 加 request schema validation，避免 content script 傳任意 action / 超長 text。
  • 把大型檔案拆成行為不變的小模組，再提高單元測試覆蓋。

UI/UX 設計師視角

核心體驗定位

翻翻吧最強的不是「翻譯一切」，而是閱讀途中遇到字詞 / 段落時，能快速理解、潤稿、留存到 Obsidian。UI 應該服務這個輕量流，不要讓設定與整頁翻譯搶走主體。

降低干擾

常駐浮球、選字 toolbar、結果卡、整頁翻譯面板可能同時出現。建議定義「單一主面板」規則：使用者當下只看到一個主要操作焦點，其餘收合成 icon。

強化信任

AI 翻譯產品的信任來自可預期：資料送去哪個 provider、是否會儲存、現在用哪個模型、錯誤如何處理。這些應在結果卡與設定頁用很短的狀態文案呈現。

設定頁資訊架構

目前痛點建議改法理由
API Key、模型、語言、Obsidian、雲端同步都在同一個大設定面拆成「快速開始」「模型與金鑰」「閱讀體驗」「留存與同步」「隱私」新手只需完成第一輪設定，進階功能不干擾主流程
多 provider 對一般使用者很抽象不加語意標籤；在模型選單旁用一句話說明模型特點，例如速度、穩定性、長文表現、是否需自備額度保持介面簡潔，讓使用者理解差異即可，不把模型包裝成過度行銷的選項
整頁翻譯 Beta 容易被誤解成成熟功能保留 Beta 標示，加上用量 / 區塊上限 / 可繼續翻譯提示預期管理會減少負評

使用者視角

新使用者最可能卡住

  • 不知道該選 Groq、Gemini 還是 OpenRouter。
  • 不知道 API Key 是否安全、會不會同步到雲端。
  • 第一次選字後若沒出現 toolbar，不知道是網站限制、暫停、還是 extension 壞了。
  • Obsidian 需要 Advanced URI，這是高價值功能，但 onboarding 要更像 checklist。

高頻使用者想要

  • 更快：常用 action 快捷鍵與最近模型切換。
  • 更安靜：特定網站停用、特定輸入框不顯示。
  • 更可控：結果卡固定、複製格式、存到 Obsidian 的模板可調。
  • 更可查：單字本、最近查詢與 Obsidian 留存之間要有清楚關係。

建議產品指標

指標評估建議預設採「本機、匿名、彙總、可關閉」：第一階段不要上傳任何使用者內容、原文、譯文、網址全文、API Key 或個人識別資訊。可以先用本機 debug panel / review checklist 人工記錄，等確定需要產品分析時，再設計明確 opt-in 的 telemetry。

指標為什麼重要可怎麼量
首次成功翻譯時間決定新使用者是否留下手動 QA 或本機匿名事件：安裝 / 設定完成 / 第一次成功回應，只記時間差與步驟，不記文字內容
選字後取消率代表 toolbar 是否干擾本機計數 toolbar 顯示、點擊 action、Esc、外部點擊；review 時看彙總數字，不上傳原文或網址
Obsidian save rate這是差異化，不只是翻譯工具本機計數結果卡顯示與儲存成功次數；不記筆記內容，只看流程轉換
敏感欄位防護觸發建立安全信任只做本機統計：略過 password / OTP / payment 欄位的次數；review 重點是防護有沒有生效

你可以怎麼 review 使用者指標

  • 第一階段用手動 QA 表：測 5 個情境，記錄成功 / 失敗 / 干擾點，不做任何資料上傳。
  • 第二階段做本機「診斷摘要」頁：顯示最近 7 天的匿名彙總，使用者可一鍵清除。
  • 第三階段若要上傳 telemetry，必須明確 opt-in，隱私政策列出欄位，且只傳事件類型、時間差、狀態碼，不傳原文 / 譯文 / URL 全文。

建議 Roadmap

Phase A / 0-3 天：P0 止血與測試入口

修 npm test 設定衝突；排除 password / OTP / payment 類敏感 input；加 sensitive input 與 XSS regression tests；確認 privacy policy / store listing 對第三方 AI provider 的資料流描述一致。

Phase B / 1 週：P1 權限面與干擾控制

新增站點停用 / allowlist 設定；把整頁翻譯改成按需初始化；收斂 web_accessible_resources；background message handler 加 schema validation、action 白名單與長度限制。

Phase C / 2-3 週：P2 可維護性與文字翻譯 UX

拆 page-translator.js 與 content.css；建立 DOM render helper；把 coverage 先拉到 65% lines；全文翻譯先專注文字段落、雙語對照、定位原文、複製雙語與失敗重試。

Phase D / 4-6 週：產品化 polish 與本機指標 review

設定頁改資訊架構；模型只保留簡潔特點說明；結果卡顯示 provider / model / privacy hint；Obsidian onboarding 做成 checklist；新增本機診斷摘要，不上傳使用者內容。

Phase E / 6-8 週：Immersive-style 文字閱讀

朝 Immersive Translate 的文字閱讀體驗收斂：段落 hover / shortcut、全文翻譯續翻、雙語密度、可讀性、長文 context digest；PDF、圖片、影片字幕延後。
